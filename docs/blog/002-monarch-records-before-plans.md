# Give Carl records before asking for a plan

Status: draft. Examples are synthetic; live household qualification and article publication are pending.

Carl needs financial records with dates and evidence before he can compare debt plans or discuss a purchase budget. The initial input is a pair of manually downloaded Monarch CSV exports: transactions and balance history. Carl's native **Import from Monarch** workflow accepts either file or both, previews changes, uses explicitly confirmed account mappings, and applies the reviewed result. A transaction ID stays an opaque identifier, even when it looks like a large number. Reimporting the same transaction does not create another purchase; an edited source row becomes a reviewable revision. A row omitted from a later export remains in history because omission does not establish deletion. Currency and account semantics need explicit mappings: these observed files do not supply enough information to infer them.

Balance rows create a different reconciliation problem. Two conflicting observations for the same source label and date do not tell Carl which amount is correct. He retains provenance, identifies the conflict, and requires a human resolution with evidence. Transactions and balances can also cover different periods, so a dashboard must state the selected scope and gaps. A card charge is spending, but its available credit is not spendable cash; a payment-like movement is not independent proof of debt repayment. These rules live in Carl's deterministic services and PostgreSQL records, shared by administration and conversation. Synthetic PostgreSQL, repeat-import and packaged UI checks verify implemented behavior; real account mappings, coverage and model handling remain unqualified. The [import contract](../MONARCH-IMPORT.md) and [acceptance evidence](../ACCEPTANCE.md) keep those boundaries explicit.
