# Public fictional household fixture

`fixtures/public-household/` is a from-scratch public synthetic dataset. The generator uses independently authored fictional people, accounts, merchants, dates, amounts and property contracts. Local inspection of the owner's financial exports informed only the supported column shapes and broad scale. This is not reversible row redaction and provides no mathematical anonymity guarantee. No private rows, labels, source hashes, mapping, exact private totals or source files belong in these fixtures.

Run `python3 scripts/generate-public-household.py --output fixtures/public-household` to reproduce every byte. The generator has no source-data argument or reader. It uses Python's standard library, explicit public text allowlists and an independently checked signed ledger. `python3 -m unittest discover -s scripts/tests -p test_public_household.py` exercises deterministic regeneration and corrupted merchant, note, tag, account identity, transfer, balance and expected-balance rejection.

## Import shapes and dates

Transactions use Carl's actual Monarch header: `Date,Merchant,Category,Account,Original Statement,Notes,Amount,Tags,Owner,Reviewed,Id`. Balances use `Date,Balance,Account`. All money is exact decimal text; account mapping provides currency and access. Exported Owner and Reviewed values never authorize sharing or approve a classification.

The dataset has 36 accounts,10920 transactions and 22365 daily balance observations. Fictional history spans January 2025 through September 2026, with opening observations on December 31,2024. Reporting uses September 2026, as-of September 30; future planning begins October 2026. IDs are fictional source identities, never original export IDs. Balances reconcile opening observation plus signed transactions to every daily closing observation. Transfer pairs have equal opposite amounts; imported omissions do not delete existing rows.

`household.json` supplies exact closing balances, shared liquid USD 136615.00, excluded private account labels and credit capacity. The fictional APR card's 60000.00 USD limit yields 47721.38 USD available credit at the selected observation. Credit capacity is borrowing, never cash. The current account schema has no typed credit-limit field: this supplied fictional limit and expired-promotion date are retained in native account evidence, while the public manifest gives the explicit expected capacity. The loader does not invent a credit-limit API. The private wallet and unknown private collectible are excluded from shared figures. USD and EUR are retained separately without conversion. A missing collectible value stays unknown.

Small separate CSVs exercise overlap, omission, explicit source correction with a multiline note, missing amount and conflicting balance observations. They are test inputs; they are not silently merged into the initial seed. Original and corrected source versions remain independently inspectable after an explicitly accepted correction.

## Homes, rentals and mortgages

Three independently fictional property records include a primary residence with no rental units, a two-unit occupied duplex, and a separate rental house vacant after its fictional lease ended. September duplex rent is 1900.00 USD against 2150.00 USD due, retaining 250.00 USD arrears. No rent due is invented for the vacant house or primary residence. Property operating expenses, maintenance and a capital improvement have explicit imported cash evidence. Future schedules distinguish estimates, committed evidence, unknown amounts and CAPEX reserve earmarks.

Each property links one existing valuation account and one existing loan account. `HomeRecords` adds supplied use and mortgage profile facts to those identities; it creates no duplicate balance, liability, rent, title or loan. Profiles support UNKNOWN, PRIMARY_RESIDENCE, RENTAL, SECOND_HOME and OTHER_REAL_ESTATE. Missing legacy profiles remain UNKNOWN. This extension does not infer a home's use from a title or reclassify the existing rental business model.

The fixture authors original principal, fixed annual rate, original amortization months, first payment, maturity, dated current principal and scheduled principal/interest payment. Observed ledger payments explicitly include additional principal. Escrow and fees are separately supplied zero assumptions. These are fictional contracts, not inferred terms. The model permits unresolved optional fields; it does not manufacture a contractual payment from missing inputs. Home/profile corrections require a serialized household permission boundary, current FINANCE manager permission, current parent and linked account access, a reviewed property revision and an idempotent request. Retained snapshots are attributed, immutable and recheck both current and historical linked account permissions.

## Application loading

`CarlPublicHouseholdSeed.seed(CarlService, Path)` is disposable preview infrastructure in `scripts/e2e`, not a production import command. Before creating any database request or record, it verifies the hardcoded canonical public-v1 SHA256 over the named, length-framed manifest, transactionCSV, balanceCSV, eventICS and reminderICS. Any altered label, note, amount or imported instruction fails closed. This hash identifies only public generated fixture bytes. It then requires an explicitly marked public-synthetic manifest and an empty prepared `Synthetic Household` with exactly two active authorized Alice/Bob members. It never wipes a database, mixes old seeds, reads credentials or calls inference providers. A persisted successful seed receipt returns the same allocated IDs on retry. Interrupted or changed seeds fail closed and require a fresh owned disposable database.

The loader uses actual FinancialRecords/MonarchImportWorkflow, RentalRecords, HomeRecords, DebtPlans, ExpenseRecords, CashPlans, BudgetRecords, FinancialGoals, FinancingOffers, PlanLifecycle and CarlService APIs. Fixture-only fixed queries retrieve exact imported identities beyond the normal 1000-row tool bound. All records use allocated database IDs. The receipt includes `memberIds`, `accountIds`, `propertyIds`, `unitIds`, `planId`, `taskIds`, `cashPlanId`, `balanceId`, artifact IDs, input scope and reporting range. Reports and drafts use a common Alice/Bob scope. Dated Bob tasks retain an obstacle; reported progress is never verified financial execution.

The loader retains a conditional cash forecast, explicit reserve 20000.00 USD and selected discretionary cap 350.00 USD. Missing future quote and excluded private inputs keep scope/obligation completeness false. Financing examples include a fictional four-month true-zero furniture offer and a hypothetical transfer with explicit fees, expiry and later APR. These are local records and comparisons; nothing pays, applies, buys, transfers, books or sends.

An offline `CalendarAgendaService.Provider` ingests `calendar.ics` through the real permission-scoped agenda service and parser. `reminders.ics` is an unbound public VTODO source; it must not be equated with an application-owned task mapping or verified completion. Root preview integration may serve both files through its owned synthetic CalDAV endpoints. No production collection is a target.

The consumer factory must call `HomeMetadata.register(instance, app, service)` before navigation assembly and grant its prepared reader SELECT only on `carl_home_view` and `carl_home_history_view`. This registers native read-only `carlHomes`, `carlHomeHistory` and the reviewed `carlSaveHomeProfile` process attached to `carlHomes`. Migration V58 adds the profile/history tables and permission-filtered views. No generic writes to raw profile/history tables are granted. The preview's public-data branch must run before its ordinary one-bill seed. The integration owner sets explicit MEMBER dashboard preferences from receipt dates/currency and permitted `planId`/`balanceId`; the integrated consumer implements these preferences.

## Verification and limits

`MAVEN_REPO=/path/to/reviewed/cache bash scripts/verify-public-household.sh` runs generator tests, checks exact generated bytes, compiles the fixture against this consumer and existing dependencies, then runs a fresh owned PostgreSQL 16 test with a 900-second JVM bound. It asserts corrupted transaction note/manifest/event/reminder rejection with zero target records or requests, native import counts, all 35 available reconciliations, shared liquidity, primary-home absence of rent/units, arrears, narration state, audience, repeat-seed nonduplication, overlap/omission behavior, explicit source revision retention, missing/conflicting-input rejection and current revocation denial. Logs remain in `target/public-household-evidence/`; raw evidence is not part of the public fixture.

Focused home tests additionally exercise optional fields, precision/currency/date rejection, simultaneous stale-revision contention, in-progress revocation serialization, replacement-loan history privacy, nonmanager denial, linked-account revocation and actual authenticated native HTTP records/process identity. HTTP stale form errors must be checked as structured errors; an HTTP 200 alone does not qualify an operation.

Controlled tests and controlled narration establish deterministic records, transport and scope behavior only. They do not qualify a live model, real institution data, completeness of a real household, legal ownership, tax treatment, credit approval, calendar provider freshness or external financial execution. Packaged UI integration and release qualification belong to the integration owner.

Canonical iCalendar fixtures use CRLF. Scoped Git attributes preserve those exact bytes on every platform and recognize CR at line endings while retaining ordinary whitespace checks. A fresh Git archive of the final signed source exactly matches all10 generated fixture files; local working-tree success alone is insufficient evidence of clone reproducibility.
