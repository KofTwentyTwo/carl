# Carl delivery contract

CircleCI composes the published Munitor `0.3.0` commands inside explicit Carl jobs. It runs fresh Java21/Maven3.9.11 dependency resolution, unchanged consumer quality/coverage, all existing PostgreSQL/browser/privacy gates, dedicated Liquibase qualification, rendered GitOps policy checks and source/dependency/application/migrator scans before publishing either image. The current parent and every fresh foundation artifact must match the reviewed upstream qualification in `config/release/foundation.json`, which retains the upstream core/adapter coverage gate; the current 0.4.1 qualification cannot qualify the 0.5.0 snapshot parent. `scripts/verify-liquibase.sh` must use the shared migrator against disposable PostgreSQL and emit `target/migration-evidence/report.json` with `status: PASS` and boolean `fresh`, `retained`, `repeat`, `checksumRejection`, `permissionIsolation`, `interruptionRetry`; absence fails before publication. The migrator reuses the exact application image and invokes `DatabaseBootstrap migrate <private-properties-file>` with `migration.engine=liquibase`. No household initialization runs at startup. Existing GitHub Actions remains active until this CircleCI path is actually qualified.

`deployment/gitops` is the source template for the separately authorized private `KofTwentyTwo/carl-CD`; register its Applications in the existing app-of-apps only after qualification. Private `carl-runtime/agent.properties`, `carl-migration/migration.properties`, `carl-ghcr` and TLS secrets contain actual discovered service settings and separate database identities. Each deployable private overlay must add a restricted `carl-backup` PreSync Job with isolated `carl-backup` credentials and a qualified immutable backup image, ordered before migration; its image must equal private qualification `backupImage`. The public scaffold omits a backup implementation because the existing cluster-wide website dump has not qualified Carl's isolation. An automation OpenPGP signer must be configured separately for signed CD commits. Private `qualification/{dev,staging,production}.json` must satisfy `image-set.py qualify`: exact source/distribution/image pair, approved namespace/host, `RETAINED_PRIVATE` data, `VERIFIED` identity, passing backup/restore, database isolation and actual workflows, plus a future explicit-timezone expiry. It contains assertions/references, never household records or credentials. Missing or fixture evidence blocks promotion. Development uses develop snapshots, staging consecutive signed RC tags, production a signed stable tag at the identical latest qualified RC source; production reuses those digests without rebuilding. Actual hosted/package/GHCR/OIDC/CD signing permissions, Authentik, retained-database upgrades and existing backup isolation/recovery remain external qualification gates; rendered manifests and synthetic CI do not establish deployment readiness.

Feature and main branch pushes run verification and scans without publication. The strict fresh-publication hold runs after those checks so missing upstream qualification still leaves useful actual test/scan artifacts. Snapshot verification/publication may use a separately reviewed `config/ci/foundation.json` with the same complete nine-artifact published qualification schema; no local cache is publication evidence and no development pin is supplied by this scaffold. RC/stable always use unchanged `config/release/foundation.json` and reject a snapshot parent. The current 0.5.0 Liquibase implementation must be published and independently qualified before a fresh hosted consumer can pass.

Sigstore signing requests CircleCI's custom `aud=sigstore` token with the root issuer `https://oidc.circleci.com`, as in the official CircleCI integration. Token claims require the live discovered Carl organization/project/pipeline definition, exact repository/ref/workflow and `ssh-rerun=false`; the certificate SAN is the pinned Carl pipeline-definition URI. A sign/verify preflight runs before either GHCR image push. Actual CircleCI environment CLI/Fulcio/GHCR behavior is a hosted qualification gate, not established by policy unit tests. Promotion verification does not require a current OIDC token. Private CD automation signing and deployment qualification remain independently required.
